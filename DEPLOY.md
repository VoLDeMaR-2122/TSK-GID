# Развёртывание ГИД Урал-ВНИИЖТ

Три части: первый администратор, создание сотрудников, деплой на сервер.

Основной путь — через Dokploy (раздел 0). Ручной путь через SSH и свой
nginx — раздел 3, на случай переезда с Dokploy.

---

## 0. Деплой через Dokploy

`.env`-файл на сервере не нужен и `deploy/nginx.conf` не нужен: переменные
задаются в интерфейсе Dokploy, а TLS и проксирование делает встроенный Traefik.

### Шаг 1. Запушить код

```bash
git push origin main
```

### Шаг 2. Создать приложение

Dokploy → Applications → Create → провайдер гита → репозиторий и ветка.
Тип сборки: **Docker Compose**, compose-файл: `docker-compose.yml`.

### Шаг 3. Переменные окружения

Вкладка Environment приложения. Обязательные (без них запуск упадёт
с понятной ошибкой):

```bash
admin_login=Заведующий
admin_password=длинный_пароль_админа
admin_name="Заведующий участком"

data_base=длинный_пароль_базы
```

Необязательные (значения по умолчанию — `gid`):

```bash
data_user=gid       # пользователь Postgres
data_name=gid       # имя базы
data_host=db        # имя сервиса Postgres внутри сети Docker
allowed_origins=https://gid.example.ru   # свой домен после шага 4
```

`data_host` в списке необязательных только потому, что он уже прописан в
`ENV` образа. Задай его явно, если сомневаешься: без него оба процесса
пытаются достучаться до `localhost:5432` внутри контейнера, где базы нет,
и сайт отдаёт 502.

`data_base` — это пароль от Postgres. Если туда положить строку
подключения вместо пароля, например
`postgresql://gid:пароль@db:5432/gid`, сервер возьмёт всё из неё, а
`data_user` / `data_name` проигнорирует. Нужно для внешней базы, например
управляемого Postgres из Dokploy.

`NEXT_PUBLIC_WS_URL` не задавать — останется пустым, и браузер пойдёт
на тот же хост по `/ws`, а Node внутри контейнера проксирует дальше на Rust.
Отдельный адрес бэкенду не нужен.

### Шаг 4. Домен

Вкладка Domains → добавить домен → сервис `app`, порт `3000`, HTTPS включён.
Сертификат Traefik выпустит сам. WebSocket (`/ws`) через Traefik работает
из коробки, ничего дополнительно настраивать не надо.

### Шаг 5. База данных

Postgres уже описан в `docker-compose.yml` (сервис `db`, данные в томе
`pgdata`) — отдельно заводить базу в Dokploy не нужно. Если позже захочешь
переехать на управляемый Postgres из Dokploy — поменяй `data_base` на строку
подключения и убери сервис `db`.

### Шаг 6. Деплой и проверка

Нажать Deploy, смотреть логи сервиса `app`: должна быть строка про создание
администратора (или что он уже был). Дальше:

1. Открыть домен — панель Гида должна загрузиться.
2. Войти логином и паролем первого администратора.
3. Завести первого сотрудника (F6 → «Сотрудники»).
4. Выйти и войти под ним.

Если вход висит: в браузере на вкладке Network соединение `/ws` должно быть
в статусе 101 Switching Protocols.

### Обновления

Новые коммиты в ветку → Redeploy в Dokploy (или автовключение redeploy
по webhook). Данные не теряются: база живёт в томе `pgdata`, пересборка
её не трогает.

### Если сайт отдаёт 502 Bad Gateway

Значит у Traefik нет живого бэкенда на порту 3000. Начни с журнала
сервиса `app` в Dokploy — по сообщениям видно, на каком шаге всё встало.

Самая частая причина — оба процесса ищут базу на `localhost:5432` внутри
контейнера, где её нет. Узнать это можно по строке в журнале:

```
[CONFIG] DB Target: localhost:5432 (User: gid, DB: gid)
```

Правильно должно быть `DB Target: db:5432`. Если так — задай в Environment
переменную `data_host=db` и нажми Redeploy.

Дальше по журналу:

| Сообщение | Причина | Что делать |
|---|---|---|
| `задайте data_base в Environment` | Compose не может стартовать без обязательной переменной | Заполнить Environment |
| `попытка 20/20 не удалась` → `FATAL ERROR` | База недоступна 40 секунд, Node сделал `exit(1)` | Проверить `data_host` и что `data_base` одинаков для сервисов `db` и `app` |
| `Bind for 0.0.0.0:3000 failed` | Задан `HOST_FRONT_PORT`, а порт на сервере занят | Убрать `HOST_FRONT_PORT` / `HOST_BACK_PORT` |
| Сборка обрывается на `rust:1-alpine` | Не хватает памяти: Rust-этап требует около 2 ГБ RAM | Добавить swap или собирать на машине побольше |

Проверить, что реально попало в контейнер:

```bash
docker exec <имя_контейнера_app> env | sort
```

### Если старт падает с «port is already allocated»

Частая причина в Dokploy: хост-порт 3000 уже держит **сам Dokploy** —
его контейнер нельзя останавливать. Проверить:

```bash
docker ps --format 'table {{.Names}}\t{{.Ports}}' | grep 3000
```

Строка вида `0.0.0.0:3000->3000/tcp` у контейнера `dokploy` — это нормально.
Строки вида `3000/tcp` без адреса (как у соседних приложений) — тоже
нормально: это внутренний порт без публикации, он не мешает.

Поэтому `docker-compose.yml` по умолчанию **не публикует хост-порты**:
Traefik ходит во внутренние порты контейнера напрямую. Если же видишь
`Bind for ... failed` — значит, в Environment заданы `HOST_FRONT_PORT` /
`HOST_BACK_PORT`, и такой порт занят. Тогда либо убери эти переменные
(вернуться к режиму без публикации), либо укажи свободный порт.

## 1. Как задать первого администратора (владельца)

Учётная запись создаётся сама при первом запуске сервера, если в базе ещё
нет ни одного администратора. Ничего вручную в базе делать не нужно.

Переменные три, все в `.env` рядом с `docker-compose.yml`:

```bash
admin_login="Заведующий"
admin_password=длинный_пароль
admin_name="Заведующий участком"
```

- `admin_login` — логин, он же ФИО. Регистр и пробелы не важны:
  `Заведующий`, `заведующий ` и `ЗАВЕДУЮЩИЙ` — одна и та же учётка.
  **Логин обязан совпадать с учёткой в базе**, иначе сервер честно
  напишет в журнал, что владелец не защищён, — и никого не защитит.
- `admin_password` — в базу не пишется, сохраняется только argon2id-хеш.
- `admin_name` — необязательно, как показывать в списке сотрудников.
- Значения с пробелами — **только в двойных кавычках**. Без кавычек
  локальный бэкенд не прочитает файл дальше этой строки.

### Что происходит при старте

```
Владелец из переменных (если такая учётка есть):
  → пометить защищённой, выдать полные права (is_admin + роль admin)
Нет активных администраторов?
├─ да  → взять логин и пароль из переменных, создать учётку владельца
│        (если логин уже есть — обновить пароль, роль и активность)
└─ нет → новых не создавать
```

Владелец **неприкосновенен**: через панель его нельзя понизить, отключить
или сбросить ему пароль — ни себе, ни другому админу. Свой пароль владелец
меняет сам (окно дежурства, нужен текущий). Матрица прав на него не действует.

### Остальные администраторы

Назначаются через панель (F6 → «Сотрудники»): создать учётку с ролью
«Администратор» или повысить существующую. Такой админ управляет всем,
но его может понизить/отключить другой админ, а владелец — тем более.
Систему без администраторов оставить нельзя: последнего отключить не даст.

### Смена пароля первого админа

Два способа.

Через переменные — если других администраторов нет: задайте новое значение
`admin_password` и перезапустите. Учётка обновится.

Через интерфейс — владелец или любой админ меняет пароль себе
через панель (текущий пароль требуется). Учётные записи других сотрудников
админ меняет из своей вкладки.

### Первый вход

Открыть сайт, ввести логин и пароль. Роль придёт с сервера — выбирать её
в форме не нужно, там только два поля.

Проверить, что всё поднялось:

```bash
docker compose logs app | grep -i "администратор"
```

В журнале должно быть, что администратор создан либо что он уже был.

## 2. Как происходит создание сотрудников

Схема простая: **новый сотрудник получает роль ДСП сразу**, остальное даёт
администратор.

### Путь сотрудника

| Шаг | Кто делает | Что происходит |
|---|---|---|
| 1 | администратор | заводит учётку: ФИО (логин), пароль, роль |
| 2 | сервер | проверяет права, хеширует пароль, пишет в базу |
| 3 | сотрудник | открывает сайт, вводит ФИО и пароль |
| 4 | сервер | сверяет пароль, выдаёт сеанс и права по роли |
| 5 | администратор | при необходимости повышает роль или отключает |

Роль `dnc` и `admin` выдаёт администратор. Сотрудник не может назначить
себе роль сам — ни через форму, ни через подделку запроса. Это проверено
тестом: клиент, приславший в запросе `role: "dnc"`, получает от сервера
ту роль, которая записана в учётке.

### Роли и что они могут (по умолчанию)

| | ДСП | ДНЦ | Администратор |
|---|---|---|---|
| Отметки прибытия/отправления | да | да | да |
| Нитки, станции, пометки | нет | да | да |
| Тревоги и оповещения | нет | да | да |
| Статистика | да | да | да |
| Управление дежурством ДСП | нет | да | да |
| Назначение ролей, учётные записи | нет | нет | да |

Таблица правится во вкладке «Права»: галочки применяются сразу всем онлайн.
У роли администратора право «Роли и права» снять нельзя, у владельца —
не действует матрица вовсе.

### Чего сервер не даст

- тронуть владельца через панель (понизить, отключить, сбросить пароль, удалить);
- удалить свою учётку и последнего администратора;
- сменить свой пароль без верного текущего;
- войти отключённой учёткой.

### Смена пароля сотрудником

Свой пароль сотрудник меняет сам: панель → смена пароля, потребуется текущий.
Забытый пароль сбрасывает администратор — сотрудник узнаёт новый от него лично.

### Вкладка «Сотрудники»

В панели администратора (открывается по F6): создание учётки (логин-ФИО,
имя, пароль от 6 символов, роль ДСП/ДНЦ/Администратор), смена роли и имени,
сброс пароля, отключение/включение, удаление навсегда (с подтверждением).
Отключённый сразу выкидывается из системы.
Ошибки сервера (например, «такая учётка уже есть») показываются прямо в панели.

## 3. Деплой вручную через docker-compose (без Dokploy)

Если Dokploy нет — тот же `docker-compose.yml` работает напрямую.

### Что нужно на сервере

Docker с плагином compose и nginx (или другой reverse-proxy).

```bash
docker --version
docker compose version
```

### Шаг 1. Положить проект

```bash
git clone <адрес репозитория> /opt/gid
cd /opt/gid
```

### Шаг 2. Создать `.env`

Файл не коммитится. Внутри — всё, что ниже:

```bash
# База данных. Пароль сюда попадает обязательно.
data_base=длинный_пароль_базы
data_user=gid
data_name=gid
# Первый администратор
admin_login=Заведующий
admin_password=длинный_пароль_админа
admin_name="Заведующий участком"

# Источники, которым разрешён WebSocket. После настройки nginx
# укажите свой домен: allowed_origins=https://gid.example.ru
allowed_origins=

# Хост-порты для ручного деплоя (в Dokploy не нужны).
# Host-nginx из deploy/nginx.conf ждёт сайт на 127.0.0.1:3000,
# а бэкенд — на 127.0.0.1:3001.
HOST_FRONT_PORT=3000
HOST_BACK_PORT=3001
```

Создать с правами 600 — в файле пароли:

```bash
chmod 600 .env
```

### Шаг 3. Поднять

```bash
docker compose up -d --build
docker compose logs -f app
```

Поднимется контейнер БД и контейнер приложения. Внутри контейнера два
процесса: фронтенд Next.js на 3000 и бэкенд на 3001.

Проверить:

```bash
docker compose ps                     # оба сервиса Up
curl -I http://127.0.0.1:3000         # отвечает фронтенд
docker compose logs app | tail -30    # нет ошибок подключения к БД
```

### Шаг 4. Nginx перед контейнерами

Порт 3001 наружу не публикуется — это осознанно. Единая точка входа — nginx:
он отдаёт сайт и проксирует `/ws` на бэкенд.

```bash
sudo cp deploy/nginx.conf /etc/nginx/sites-available/gid
sudo nano /etc/nginx/sites-available/gid      # вписать свой домен
sudo ln -s /etc/nginx/sites-available/gid /etc/nginx/sites-enabled/gid
sudo nginx -t && sudo systemctl reload nginx
```

Заголовки `Upgrade` и `Connection` в конфиге обязательны — без них
WebSocket-соединение не установится, и вход будет бесконечно «висеть».

### Шаг 5. HTTPS

Сертификат бесплатный:

```bash
sudo certbot --nginx -d gid.example.ru
```

Certbot сам поправит конфиг. После этого клиент будет ходить по
`wss://gid.example.ru/ws` — адрес собирается из адреса страницы, так что
ничего пересобирать не нужно.

### Шаг 6. Проверить вход

1. Открыть сайт снаружи — панель Гида должна загрузиться.
2. Войти логином и паролем первого администратора.
3. Завести первого сотрудника.
4. Выйти и войти под ним: должно хватить роли ДСП.

Если вход не проходит, смотри в консоли браузера на вкладке Network:
соединение `ws://…/ws` должно быть в состоянии 101 Switching Protocols.

### Обновление на новой версии

```bash
cd /opt/gid
git pull
docker compose up -d --build
```

Данные не теряются: база лежит в томе `pgdata`. Учётные записи, роли и
график переживают пересборку.

### Важные предостережения

**Не правьте `NEXT_PUBLIC_WS_URL` без нужды.** Эта переменная встраивается
в бандл Next.js при сборке и выполняется в браузере посетителя. Если
вписать `ws://127.0.0.1:3001/ws`, то подключаться будет к компьютеру
посетителя, а не к серверу. По умолчанию переменная пустая, и клиент сам
берёт адрес текущей страницы — это правильный режим.

**Пароль базы из репозитория удалён.** Раньше `gidpass` лежал прямо в коде;
теперь он только в `.env` на сервере.

**Не храните `.env` в git.** Он в `.gitignore`.

### Если нужен отдельный адрес для бэкенда

Тогда адрес известен заранее и клиент должен ходить напрямую:

```bash
NEXT_PUBLIC_WS_URL=wss://api.gid.example.ru/ws
```

и тогда бэкенд надо публиковать (`3001:3001`) и разрешить его origin в
`allowed_origins`. Один адрес через nginx проще и безопаснее.
