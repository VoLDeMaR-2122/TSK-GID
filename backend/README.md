# GID backend (Rust)

Вся серверная логика ГИД Урал-ВНИИЖТ: учётные записи, проверка паролей,
права доступа, WebSocket-синхронизация и работа с PostgreSQL. Отрисовка
остаётся на Next.js в корне репозитория.

## Учётные записи

Каждый сотрудник входит по **логину (ФИО) и паролю**. Роль клиент не выбирает:
она читается из учётной записи, иначе любой мог бы объявить себя админом.

| Поле | Назначение |
|---|---|
| `login` | нормализованное ФИО: регистр, лишние пробелы и типографские тире не важны |
| `password_hash` | argon2id со случайной солью; открытого пароля в базе нет |
| `role` | `admin` / `dnc` / `dsp`, назначает администратор |
| `is_admin` | признак администратора, ставится только при развёртывании |
| `active` | отключённая запись не может войти и выкидывается из сеанса |

### Первый администратор

Создаётся автоматически при первом запуске, если в базе ещё нет ни одного
администратора:

```bash
GID_ADMIN_LOGIN=Заведующий
GID_ADMIN_PASSWORD=пароль
GID_ADMIN_NAME="Заведующий участком"
```

В docker-compose эти переменные уже прокинуты, достаточно задать их в `.env`.
Пароль сохраняется только как argon2id-хеш. При повторном развёртывании с теми
же переменными учётная запись обновляется — можно rotate пароль, не заходя в базу.

Если администраторов уже нет, но переменные заданы — запись приводится к
активной админской: это позволяет восстановить доступ.

### Что нельзя

- выдать роль `admin` через панель — только переменными окружения;
- отключить **последнего** администратора;
- сменить свой пароль без верного текущего.

Новый сотрудник сначала получает роль `dsp` — её назначает администратор
через панель или командой `accountCreate`. Права `dnc` и `admin` выдаёт админ.

## Запуск

```bash
npm run backend:dev          # разработка с пересборкой
npm run backend:build        # release-сборка
npm run backend:check        # clippy

# проверка протокола (нужна учётка ДНЦ)
GID_LOGIN=... GID_PASSWORD=... node backend/protocol-check.mjs ws://127.0.0.1:3001/ws

# проверка входа и управления сотрудниками (нужны данные первого админа)
GID_ADMIN_LOGIN=... GID_ADMIN_PASSWORD=... node backend/auth-check.mjs ws://127.0.0.1:3001/ws
```

Переменные окружения читаются из `.env.local` в корне: `DB_HOST`, `DB_PORT`,
`POSTGRES_*`, `BACKEND_PORT`, `BACKEND_HOST`, `GID_ALLOWED_ORIGINS`,
`GID_ADMIN_*`.

## Протокол

Входящие: `login` (логин+пароль), `resume` (продлить сеанс), `logout`,
`passwordChange`, `accountCreate`, `accountPatch`, `accountSetPassword`,
`userPatch`, `kick`, `state`, `alertAdd`, `alertUpdate`, `alertToggle`, `alertRemove`.

Исходящие: `hello`, `loginOk`, `authError`, `sessionExpired`, `capabilities`,
`accounts`, `state`, `alerts`, `presence`, `audit`, `forbidden`, `notice`.

Правила проверки прав живут только в `permissions.rs` и `ws.rs`. Клиент получает
готовый список своих прав в `capabilities` и лишь прячет ненужные пункты меню —
настоящая проверка всегда на сервере.

## Таблицы

`stations`, `trains`, `train_stops`, `marks`, `alerts`, `audit_log`,
`persons` (учётные записи), `users` (журнал сеансов).

При старте вычищаются сеансы старой системы, где роль ставил клиент: в них
накопилось 14 записей с ролью `admin`, которые иначе стали бы настоящими
администраторами.

## Структура

| Файл | Назначение |
|---|---|
| `src/main.rs` | конфиг, запуск, роутинг |
| `src/accounts.rs` | нормализация логина, argon2id, требования к паролю |
| `src/permissions.rs` | роли и матрица прав |
| `src/models.rs` | структуры данных и сериализация в camelCase |
| `src/db.rs` | схема таблиц, запросы, транзакции, первый админ |
| `src/hub.rs` | реестр сокетов и кэш пользователей |
| `src/ws.rs` | протокол, обработчики, проверка прав |
